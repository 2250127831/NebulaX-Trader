# SPSC 跨回绕空洞方案: 技术债记录

2026/8/3 — `ut_byte_ring_pipeline` flaky 的根因与临时妥协

## 一句话结论

**SPSC 字节 ring 的"消息级跨回绕消费"存在固有竞态,空洞方案(浪费空间换稳定性)是临时妥协。日后需要更彻底的方案。**

## 问题

`ut_byte_ring_pipeline`(纯内存管道测试,不走 UDP)偶发 `parsed_count < expected`(少几条~几百条),概率性 flaky。

- 1MB ring + 7MB 数据(频繁回绕):**6~12/30 失败**
- 8MB ring(7MB 数据一次装下,无回绕):**30/30 稳定**

**结论:跨回绕是触发条件。**

## 根因(深挖过程)

1. **消费语义差异**:撮合引擎 SPSC 用**流式消费**(读连续 chunk,分两次发),本项目用**消息级消费**(要求完整消息)。撮合引擎从不拼消息,无此问题。
2. **跨回绕拼段竞态**:本项目跨回绕时手动拼"尾部 + 物理开头"(`memcpy(tmp+n1, raw_buffer(), n2)`),消费者读物理开头头部段时,生产者可能并发写入物理开头 → 读到错位数据 → 损坏头丢弃 → head 错位(每次+4)→ 累积丢消息。
3. **误导线索**:
   - push 的 `used` 诊断从不为负/不超容量 → 排除下溢(commit 9fed8e7 误判,实际未发生)
   - read_release 从不过度释放 → 排除
   - 各种修复(手动拼段/pop/分两段消费/发布验证)都只降概率,未根治

## 临时方案(83d4c02): 空洞约定

**生产/消费者约定**,消息 `[4头: seq(2)+len(2)] + body`,`len=0` 是空洞标记:

```
生产者 push 跨回绕(pos + len > capacity):
  尾部剩余 >= 4 → 写空洞头 [len=0], tail 跨越到下一圈物理开头
  尾部剩余 <  4 → 直接跳过(不用 <4 的尾部), tail 跨越
  memcpy(buf_, data, len) 写消息到物理开头
  tail = aligned + len (aligned = 下一圈开头)

消费者 parse:
  读到 len==0 → 空洞, head 跳到下一圈开头
  读头时 read_acquire(4) < 4 → 必是空洞(生产者不用 <4 的尾部, 无歧义), 跳过
  消息永不跨回绕 → 无拼段竞态
```

**验证**:1MB ring 下 **100/100 稳定**,15/15 测试过,246MB 生产压测正常。

## 妥协点(为什么是临时的)

- **浪费空间**:跨回绕时尾部剩余空间(可能接近 capacity)被空洞跳过,ring 有效容量下降。
- **未根治语义**:空洞是"避开跨回绕",不是解决"消息级跨回绕"本身。
- **耦合约定**:push 假设调用方传完整消息(4头+body),空洞标记是消息格式约定,非通用字节 ring。

## 日后再排查的方向

1. **流式消费对齐撮合引擎**:parser 改成"读连续部分,跨回绕分两次解析"(但 ITCH 消息不可拆,需改解析模型)。
2. **push 保证消息原子可见**:单次 push 完整消息 + 空间不足忙等(已试,不解决头部段竞态)。
3. **跨回绕消费加同步**:无锁 SPSC 下难,需屏障或锁。
4. **空洞变体**:空洞头用更紧凑的标记,或空洞区域可被后续小消息复用(降低浪费)。
