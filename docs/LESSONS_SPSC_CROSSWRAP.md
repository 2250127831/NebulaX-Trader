# SPSC 跨回绕空洞方案: 技术债记录

2026/8/3 — `ut_byte_ring_pipeline` flaky 的根因与方案演进

## 一句话结论

**SPSC 字节 ring 跨回绕时,竞态来自"头帧跨回绕"(不是消息体跨回绕)。对照实验证明:头帧不跨回绕即稳定(150/150)。当前用"实验A方案"(头帧不绕,消息体可绕)取代空洞方案,浪费更少。**

## 问题

`ut_byte_ring_pipeline`(纯内存管道测试,不走 UDP)偶发 `parsed_count < expected`(少几条~几百条),概率性 flaky。

- 1MB ring + 7MB 数据(频繁回绕):**6~12/30 失败**
- 8MB ring(7MB 数据一次装下,无回绕):**30/30 稳定**

**结论:跨回绕是触发条件。**

## 根因(深挖过程)

1. **消费语义差异**:撮合引擎 SPSC 用**流式消费**(读连续 chunk,分两次发),本项目用**消息级消费**(要求完整消息)。撮合引擎从不拼消息,无此问题。
2. **跨回绕拼段竞态**:本项目跨回绕时手动拼"尾部 + 物理开头"(`memcpy(tmp+n1, raw_buffer(), n2)`),消费者读物理开头头部段时,生产者可能并发写入物理开头 → 读到错位数据 → 损坏头丢弃 → head 错位(每次+4)→ 累积丢消息。
3. **误导线索**:
   - push 的 `used` 诊断从不为负/不超容量 → 排除下溢(commit 9fed8e7 误判,实际未发生)
   - read_release 从不过度释放 → 排除
   - 各种修复(手动拼段/pop/分两段消费/发布验证)都只降概率,未根治

## 对照实验(定位竞态来源)

设计两个半空洞实验,隔离"头帧回绕" vs "消息体回绕":

| 实验 | 头帧 | 消息体 | 1MB ring 150次 |
|---|---|---|---|
| **A** | 不跨回绕(尾部≥4写头帧) | 可跨回绕 | **150/150 稳定** |
| **B** | 可跨回绕(尾部<4拆头) | 不跨回绕(空洞) | **85/100 flaky** |

**结论:竞态来自"头帧跨回绕",不是消息体跨回绕。**
跨回绕时,头帧的物理开头部分(4-n 字节)被生产者并发覆盖 → 消费者拼头读到错位数据 → seq/body_len 错乱 → 丢消息。消息体跨回绕无害(读到的体是数据,不影响定位)。

## 当前方案(实验A): 头帧不绕,消息体可绕

```
生产者 push 跨回绕(pos + len > capacity):
  尾部剩余 >= 4 → 头帧写尾部(不跨回绕), 消息体跨回绕(尾部剩余+物理开头)
  尾部剩余 <  4 → 跳过尾部, 头+体都到物理开头

消费者 parse:
  头帧 n==4 完整读; n<4 且 used>=4 → 尾部空洞(尾部<4被跳过), 跳到物理开头
  消息体跨回绕 → 拼段(尾部体 + 物理开头体)再解析
```

**验证**:1MB ring 下 **150/150 稳定**,15/15 测试过,246MB 生产压测正常。

**相比空洞方案的优点**:尾部剩余 ≥ 4 时复用(头帧+部分体),只有尾部 < 4 才浪费(≤3字节),浪费更少。

**注意**:push 假设"消息 = 前4字节头 + body"(硬编码)。这是与调用方(feed)的约定,非通用字节 ring。

## 遗留的技术债

- **头帧"不跨回绕"是约定,非通用语义**:push 硬编码前4字节为头,限制了通用性。
- **消息体跨回绕的拼段仍在**:虽然稳定,但拼段读物理开头仍依赖"生产者已发布"验证。
- **未证明消息体跨回绕为何稳定**:实验A稳定,但理论解释(体读错位无害)还需验证——可能体拼段也有极窄竞态,只是概率更低。

## 日后再排查的方向

1. **流式消费对齐撮合引擎**:parser 改成"读连续部分,跨回绕分两次解析"(但 ITCH 消息不可拆,需改解析模型)。
2. **头帧格式解耦**:push 不硬编码4字节头,改为通用"前缀对齐"语义。
3. **跨回绕消费加同步**:无锁 SPSC 下难,需屏障或锁。
4. **验证消息体拼段的安全性**:对照实验只证明"头不绕稳定",体拼段的极端时序是否也有竞态需进一步验证。
