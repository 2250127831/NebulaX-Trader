# Tick 数据源选型决策

## 选型结论

- **选择**：NASDAQ ITCH 协议
- **接入方式**：UDP 原始二进制流（io_uring 接收）
- **交易对手方**：信号发出后，成交回报来自外部（回测 = 撮合引擎 / 实盘 = 交易所广播）。交易系统不模拟撮合，靠成交回报重建自己的订单簿，见 §2.5
- **定位**：从网卡到网卡的全链路低延迟策略管道

---

## 1. 选型历程

### 1.1 最初考虑：openctp TTS + CTP C++ API

| 优点 | 缺点 |
|------|------|
| 免费模拟 Tick + 交易 | CTP .so 黑盒，无法优化网络层 |
| A 股全品种覆盖 | io_uring/DPDK 落地不了 |
| CTP C++ API 二进制协议 | 闭源私有协议，格式不公开 |

### 1.2 问题

CTP 的 .so 将网络层完全封装，意味着项目的核心技术——io_uring 收包、零拷贝解析、内核旁路——全都没有落地场景。项目变成"调 .so 回调的策略脚本"，而非低延迟交易基础设施。

### 1.3 转向：NASDAQ ITCH

ITCH 是全球低延迟交易领域的标准协议，架构完全开放：

| 对比项 | CTP .so | ITCH 开放协议 |
|--------|---------|---------------|
| 协议格式 | 闭源二进制，未公开 | 公开，文档完整 |
| 网络层 | .so 封装，无法介入 | UDP 原始包，全链路可控 |
| io_uring | 用不上 | 从头到尾可用 |
| DPDK/Kernel Bypass | 用不上 | V6 目标 |
| 免费压测数据 | 无 | NASDAQ 官方提供样本二进制数据 |
| 面试认可度 | 国内量化熟悉 | 全球量化团队都认 |

### 1.4 不对等关系

| 场景 | 方案 |
|------|------|
| 开发期管道调试 | ITCH 样本数据回放 |
| 解析器开发 | ITCH 协议文档 + 样本二进制包 |
| 吞吐压测 | ITCH 样本（一天千万级逐笔成交） |
| 全链路延迟测量 | 云服务器发 ITCH → 本机网卡收 → 管道 → 信号发出 → 网卡时间戳 |
| 迁移到 A 股 L2 | 技能可迁移（二进制协议解析 + io_uring + 无锁管道全部复用） |

## 2. 项目边界

### 本项目的范围（NX-Trader）

```
Tick 二进制流 ──→ [网卡 t1]
  → io_uring 收包
  → 零拷贝 ITCH 解析
  → SPMC 无锁广播
  → 多个 Worker 并行运行策略
  → RiskManager 检查（仓位/亏损）
  → OrderManager 记录订单
  → ExecutionEngine 发出信号 [网卡 t2]
```

**t1 ~ t2 之间的全链路是本项目的范围**。成交回报来自外部（回测 = 撮合引擎 / 实盘 = 交易所广播），交易系统靠回报重建订单簿、同步持仓，不模拟撮合逻辑，见 §2.5。

### 边界外的职责

| 模块 | 归属 |
|------|------|
| 订单簿撮合 | NebulaX（独立项目） |
| 交易所连接（CTP/XTP） | 执行系统（后续可对接） |
| 成交回报处理 | 执行系统 |
| PnL 统计 | 执行系统或独立模块 |
| 历史数据回测 | 回测框架（独立） |

## 2.5 核心区分：撮合引擎（产生成交）vs 交易系统（观察成交）

> 这是两个项目的根本分界，也是「为什么交易系统的订单簿靠外部重建」的根源。
> 忘了这条，就会把撮合引擎的能力错误地搬进交易系统。

### 两个角色

| | 撮合引擎（NebulaX） | 交易系统（本项目 NX-Trader） |
|---|---|---|
| 角色 | **交易所**（撮合者） | **客户**（观察者） |
| 成交怎么来 | **自己产生**（撮合算法，价格-时间优先） | **外部接收**（交易所 / 撮合引擎广播） |
| 订单簿来源 | **自己维护**（撮合动作的状态） | **外部重建**（听成交 + 委托重建） |
| 能否「决定」成交 | 能（它撮合的） | 不能（它只是看） |

一句话：**撮合引擎是「产生成交的一方」，交易系统是「观察成交的一方」。**
前者自己撮合、簿是自己的；后者不撮合、簿靠外部记录重建。

### 由此推出的三点结论

1. **交易系统不能模拟撮合逻辑。** 真实市场的撮合在交易所那里，它只能接收交易所广播的成交记录来了解市场发生了什么。模拟撮合是撮合引擎的职责，不属于交易系统。

2. **交易系统的订单簿永远是「重建」的，不是「拥有」的。** 不管外部是真实交易所还是回测里的撮合引擎，它都只能靠外部成交 + 委托流重建市场快照。因此它**无法知道簿的全部细节**（某一档每一笔挂单是谁的、剩余多少），只能知道「这个价位有多少量」。

3. **撮合引擎的簿和交易系统的簿是两个簿，不能共用。** 不是数据结构不同，而是**信息精确度不同**：撮合引擎知道全部（它造出来的），交易系统只知道重建出来的近似。回测里「交易系统靠监听撮合引擎的成交回报重建自己的簿」，两个簿是独立的——共享内存是进程间传输的手段，不是簿的归属。

### 对数据消费的意义

- 逐笔委托流（A/D/X/U）＝订单簿的**原材料**：重建「有哪些挂单、在什么价位、多少量」。它是订单簿唯一可靠来源。
- 成交流（P/E/C）＝订单簿的**辅助**：更新最新价、成交量、部分成交后的剩余量。
- **只有成交流无法重建订单簿**：成交消息不告诉你「哪一笔挂单被吃了、剩余多少」，不知道别人委托的数量，就无法判断全部成交还是部分成交。
- 撮合引擎重放自己的逐笔委托流即可精确重放簿；交易系统在回测里重放撮合引擎的完整委托流才能保证簿准确。

## 3. 性能测量方法

### 测量目标

从 Tick 包到达网卡（t1）到策略信号离开网卡（t2）的间隔。

### 测量方法

```cpp
// 接收端：SO_TIMESTAMPING 取 t1
setsockopt(sock, SOL_SOCKET, SO_TIMESTAMPING, ...);
recvmsg(sock, &msg, 0);
// msg 中取出 t1（内核在网卡中断打的时间戳）

// ... 整个管道处理 ...

// 发送信号：SO_TIMESTAMPING 取 t2
sendto(sock, signal, len, 0, ...);
// send 完成时从 cmsg 取出 t2（网卡发送完成时间戳）

// 延迟 = t2 - t1
```

### 测试环境的组成

| 组件 | 作用 |
|------|------|
| 海外云服务器 | 以 UDP 高速回放 ITCH 样本数据 |
| 本机 | 运行 NX-Trader 完整管道 |
| ITCH 样本数据 | NASDAQ 官方发布的历史逐笔成交包 |

云服务器只负责发包，不参与延迟测量。t1 和 t2 都在本机网卡上取，网络传输不进入测量结果。

### 测量结果的解读

延迟来自于：

```
网卡收到包 → 内核协议栈 → 用户态 recv → 解析 → SPMC 入队
  → 策略 Worker 出队 → on_tick → 信号 → Risk → Order → send
```

每个环节都可以通过时间戳拆分，V1 即开始全链路延迟测量。


## 4. 未来迁移到 A 股 L2

ITCH 上积累的能力全部可迁移：

| ITCH 技能 | A 股 L2 对应 |
|-----------|-------------|
| UDP 二进制收包 | 同，io_uring 复用 |
| 消息类型码解析 | 换协议类型表 |
| 逐笔成交解析 | 深交所 STEP / 上交所 LWSP |
| 时间戳对齐 | 同 |
| 无锁管道分发 | 完全复用 |
| 策略调度 | 完全复用 |
